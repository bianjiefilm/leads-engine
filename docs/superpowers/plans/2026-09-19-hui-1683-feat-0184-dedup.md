## 目标(本票只做)

**线索 intake 的事件去重规则 + 联系人关联/合并规则**,以领域函数 + HTTP API 形式交付:

- **事件幂等键 = (接收租户, 来源 app, 来源命名空间, event_id)**;重复投递不重复建线索;
  同键同内容(content_sha256)→ 幂等吞,返回原引用;同键**异**内容 → 显式冲突(409),不静默覆盖。
- **联系人查重仅在所属租户内**(同手机号跨租户互不可见、不合并、不绑定平台账号)。
- **三分类**:
  - `exact_duplicate` 重复事件 —— 幂等吞,返回原 lead/contact 引用,零写入;
  - `repeat_consult` 同一联系人再次咨询 —— **新建 lead** 关联同一 contact,
    新 lead 保留自己的来源/活动/授权记录(真实咨询次数不丢);
  - `ambiguous` 疑似同人 —— 共享号码多命中:**新建 contact + lead**(不丢真实咨询),
    写 merge_candidates 候选,**绝不静默合并**;
  - (零命中的普通新线索记 `new`,属于"非去重结果"的记账值,三分类管的是去重判定本身。)
- **合并是显式、owner 专属、可审计、可纠错**的动作:字段级 provenance、lead/consent 重指计数、
  两侧合并前快照;**consent 取最严格**:任一侧存在 revoked → 合并后有效状态 revoked,
  marketing_allowed 取 AND;per-source consent 行**随 contact 重指、不归并语义**
  (1691 交接要求逐字落实:撤销不可逆在合并后依然成立)。
- 提供候选池查询/关闭(merged/dismissed)与重复统计;undo(仅未发生后续写时)。

**不做**:接收渠道本身/inbox(HUI-1680;本票导出 `IntakeLeadInTx` 供其同事务调用)、
手机号模糊搜索、跨商家合并、平台账号绑定、自动触达。

## 硬边界(验收红线)

1. **同键异内容必须显式冲突**(409 `event_content_conflict`),绝不静默覆盖原事件。
2. **多命中绝不静默合并**:ambiguous 只建候选池行,合并必须 owner 显式调用。
3. **查重空间 = 本租户**:candidate 查询一律带 tenant_id;跨租户同号码各建各的 contact。
4. **consent 红线沿用 1691**:revoked_at 一旦存在,任何重放/合并/重指都不得清除或改写;
   合并后重放旧 consent 事件仍然只能 replay_unchanged。
5. **手机号不入 URL/日志**:intake 日志只记 class/幂等键/id/phone 指纹(HMAC)前缀;
   列表/查询面无 phone 参数(沿用 1691 rejectPhoneSearch 纪律,新端点同样不收)。
6. **权限**:intake = ActionCreate(租户内);merge/undo/候选池/统计/关闭候选 = 新增
   authz.ActionMerge,**owner-only**(与 export/delete 同级,租户级行为)。
7. **原子性**:事件行 + lead + contact + consent + 候选行在**同一事务**内完成
   (与 1680 的 inbox 写入共享同一 *sql.Tx,即 `IntakeLeadInTx(tx, …)` 接缝)。

## 数据模型(迁移 0005,全部 additive)

- `lead_intake_events`:
  `(id, tenant_id→tenants, source_app, source_ns, event_id, content_sha256, phone_fpr,
  class CHECK IN (new,exact_duplicate,repeat_consult,ambiguous), lead_id→leads,
  contact_id→contacts, created_at, UNIQUE(tenant_id,source_app,source_ns,event_id))`。
  `phone_fpr` = HMAC-SHA256(pepper, 归一化手机号) 的 hex —— intake 索引不落明文手机号。
- `merge_candidates`:
  `(id, tenant_id, contact_a, contact_b, reason, status CHECK IN (pending,merged,dismissed),
  created_at, resolved_by, resolved_at, UNIQUE(tenant_id,contact_a,contact_b,reason),
  CHECK(contact_a < contact_b) 字典序规范对)`。
- `contact_merges`(审计主体):
  `(id, tenant_id, target_contact, source_contact, field_provenance JSON,
  target_before JSON, source_before JSON, lead_repoint_count, opp_repoint_count,
  consent_repoint_count, followup_repoint_count, repointed_lead_ids JSON,
  repointed_consent_ids JSON, merged_by, merged_at, undone_at, undone_by)`。
  两侧快照使 undo 忠实可回放;重指 id 列表使 undo 精确回指。

## 领域函数(store 层,与 1680 的接缝)

```go
// internal/store/lead_intake.go
type IntakeInput struct { TenantID, SourceApp, SourceNS, EventID string;
    Content []byte; ContactName, Phone, Email, BusinessCategory string;
    SourceRefID string; Consent *ConsentUpsert; Pepper string }
type IntakeResult struct { Class string; LeadID, ContactID string; Duplicate bool }
var ErrEventContentConflict = errors.New(...)  // HTTP → 409
func IntakeLeadInTx(tx *sql.Tx, in IntakeInput) (IntakeResult, error)
```

流程:幂等键查重(同键同 sha → 返回原引用 exact_duplicate;异 sha → conflict)
→ 本租户内按归一化手机号查活 contact(0 命中 → 新 contact+lead, class=new;
1 命中 → 新 lead 关联, class=repeat_consult;多命中 → 新 contact+lead + 候选行, class=ambiguous)
→ 同键并发插入撞 UNIQUE → 重读返回既有(幂等)。全部零独立 Commit —— 事务归调用方。

## HTTP API(/api/v1,真实服务 E2E)

- `POST /leads/intake`(ActionCreate):幂等键 + contact 事实 + 可选 source/consent;
  200=幂等命中 / 201=新建 / 409=content conflict;400=键缺失或字符集非法。
- `POST /contacts/{id}/merge/{otherId}`(ActionMerge, owner-only):字段级 provenance,
  target 缺字段由 source 补;coarse consent_status 取最严格(denied>pending>granted);
  source 侧脱敏墓碑(行保留,可由 undo 快照恢复);返回 merge 审计记录。
- `POST /merges/{id}/undo`(ActionMerge):仅未发生后续写(target 行未被改、无新
  lead/consent/followup/merge 指向 target)时允许;恢复 source/target/leads/consents;写 undo 审计。
- `GET /merge-candidates`、`POST /merge-candidates/{id}/dismiss`、`GET /dedup/stats`(均 ActionMerge)。
